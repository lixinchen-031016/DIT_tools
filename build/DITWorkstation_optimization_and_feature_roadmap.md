# DIT 工作站优化与功能添加路线报告

> 版本：v1.0
>
> 日期：2026-08-15
>
> 范围：`DIT_tools` / `DITWorkstation`（PySide6 + SQLite 本地桌面应用）

## 1. 执行摘要

项目已经具备可用且覆盖完整的 DIT 工作流：项目与工作区、媒体导入、多目标备份、校验、RAW 提取、重命名、检索、素材信息、归档恢复、模板、审计、个人/团队模式和报告生成。核心服务分层明确，归档安全防护、SQLite 连接池、备份断点续传和迁移备份设计可靠。

下一阶段不应优先扩展更多孤立功能，而应先完成两条主线：

1. **数据安全与可恢复性**：让配置损坏、误删、路径变化、任务失败都可诊断、可恢复、可追溯。
2. **大项目响应性与任务一致性**：让万级至十万级素材项目在检索、浏览、导出、校验、归档时保持界面可用、可取消、可恢复。

在这两条主线稳定后，再交付审计日志查看器、真实备份报告、计划完整性校验、增量备份等高价值功能。云同步、多用户协作和独立个人版暂不进入近期范围，因为现有本地 SQLite、全局配置与无身份模型尚不具备相应基础。

## 2. 评估依据

本报告基于以下材料和代码路径交叉核查：

- `code_analysis_report.md`
- `README.md`、用户手册和功能模式设计文档
- `DITWorkstation/DITWorkstation/Services/`
- `DITWorkstation/DITWorkstation/Views/`
- `DITWorkstation/DITWorkstation/ViewModels/`
- `DITWorkstation/DITWorkstationTests/`
- `.github/workflows/ci-cd.yml`

本地全量测试结果：`335 passed`，耗时约 3.15 秒。唯一警告是执行环境禁止写入仓库根 `.pytest_cache`，不属于应用功能失败。

## 3. 当前状态

### 3.1 已有优势

- 服务层与 UI 基本分离，数据模型、服务、视图模型和 Qt 视图职责清楚。
- SQLite 使用线程级连接复用、WAL、`busy_timeout`、事务封装及迁移前备份。
- 归档恢复已防御路径穿越、zip bomb、符号链接越界，并使用临时目录后再落盘。
- 备份具备多目标并发、断点续传、任务快照、失败重试、校验和与空间预检。
- 迁移使用 `PRAGMA user_version`，已覆盖历史字段、标签、FTS、备份模板等升级路径。
- 现有测试覆盖服务层、迁移、备份恢复、归档安全、Qt 无头交互、功能模式与线程生命周期。

### 3.2 已确认的主要缺口

| 类别 | 现状 | 后果 |
|---|---|---|
| 大项目读取 | `get_media_assets(project_id)` 全量读取；素材信息、归档、报告、校验、日志关联均使用它 | 万级素材下内存增长、主线程卡顿、长时间无响应 |
| UI 长任务 | `TaskViewModel` 仅用于备份；导入、重命名、归档、报告、RAW 等各自管理线程 | 取消、错误、资源释放、任务记录的行为不一致 |
| 丢失素材 | 可检测并清理数据库记录，但不能重新链接到已移动的文件 | 用户可能以删除替代恢复，损失元数据关联 |
| 破坏性操作 | 项目/素材记录删除和文件重命名没有统一撤销模型 | 误操作恢复成本高 |
| 配置可靠性 | `settings.json` 读取失败后静默返回空配置，写入不是原子替换 | 配置损坏难发现，存在部分写入风险 |
| 备份重试 | `retry_failed_files` 仍重新扫描整个源目录 | 大卡重试产生冗余 I/O，拔卡后恢复时间长 |
| 报告闭环 | 备份报告视图未传入真实备份历史 | 用户看到的报告与实际作业记录不一致 |
| 发布质量 | CI 仅在 Ubuntu/Python 3.11 执行 pytest；无 lint、类型、安全扫描和跨平台运行冒烟 | 本地 Python 3.13、macOS、Windows 问题可能在发布后暴露 |

### 3.3 对既有静态报告的修正

以下结论仍然有效：宽泛异常过多、`DatabaseService` 和部分视图过大、文件扫描与线程池循环存在重复、分页治理必要、配置与迁移错误应更可见。

以下结论需要修正或重新排序：

- CSV 导出已经通过 `iter_search_assets` 流式迭代，不会先将全部搜索结果物化为列表；真正问题是它仍在 UI 主线程执行。
- 默认校验算法已经是 XXHash64。MD5 保留作兼容用途即可，不需要作为近期迁移任务。
- UPDATE 字段白名单遗漏会导致字段被忽略或无法更新，不会直接构成 SQL 注入；它应按维护性和契约一致性治理。
- README/CI 注释中旧测试数量已经漂移，应改为动态或实际统计，不应继续维护易过期的硬编码数字。

## 4. 路线原则

1. 数据不丢失优先于操作便利，任何删除和路径修改都必须可审计。
2. 先建立公共能力，再扩展功能；不要在每个视图重复实现线程、扫描、分页和错误处理。
3. 大项目功能必须以流式、分批、可取消为默认，而不是事后优化。
4. 数据库模式变更必须版本化、可回滚、可验证，并保留旧版本测试样本。
5. 以真实工作流验收：插卡、导入、备份、校验、整理、交付和恢复，而非只验证单个函数。
6. 避免“大爆炸式”重构；`DatabaseService` 先建立清晰接口与测试边界，再逐步拆分。

## 5. 分阶段实施路线

### 阶段 0：基线、契约与观测（3-5 人日）

目标：量化当前瓶颈，避免在没有数据的情况下优化。

交付：

- 构建可重复的合成数据集：1 万、5 万、10 万条媒体记录，以及多层目录和混合格式样本。
- 记录导入、项目打开、检索、翻页、CSV 导出、完整性校验、归档的耗时、峰值内存和取消延迟。
- 定义服务层错误结果契约：成功、未找到、冲突、参数错误、磁盘/数据库错误、已取消。
- 建立任务基线：任务状态、开始/结束时间、错误摘要、关联项目、可恢复信息。

验收：

- 基准可在 CI 或本地指定命令重复运行并输出 JSON/Markdown 结果。
- 所有后续性能 PR 能对比阶段 0 基准，明确没有回退。

### 阶段 1：数据安全与可恢复性（8-12 人日）

目标：消除“静默丢失”和“无法恢复”的关键风险。

交付：

- 设置服务：JSON schema/字段类型校验、临时文件写入并原子替换、损坏文件重命名为 `.corrupt.<timestamp>`、启动提示与默认值回退。
- 数据库结果模型：引入 `OperationResult` 或领域异常；更新/删除接口区分不存在、冲突与基础设施错误。
- 丢失素材重新链接：用户选择新根目录，按相对路径、文件名/大小、可选校验和匹配；提供预览、冲突决议、批量回写和审计日志。
- 数据库回收站：素材和项目删除先软删除，保存必要快照；支持恢复和到期清理。初版只管理数据库记录，不自动删除源媒体文件。
- 重命名回退：保存每次重命名的 old/new 映射；只允许回退未被后续修改、且目标状态可确认的文件。
- 数据库操作日志增加结果状态、关联对象 ID 和恢复关联 ID。

验收：

- 损坏设置不会被静默覆盖，用户能找到保留的原文件。
- 批量删除和项目删除可在规定保留期内恢复元数据、标签、日志关联和备份位置。
- 对移动后的 1000 个素材，可在不删除记录的情况下完成重定位并生成冲突报告。
- 取消或异常退出后不存在“显示成功但未落库”的写操作。

### 阶段 2：大项目响应性（10-15 人日）

目标：让资产规模从数千条扩展到十万条仍可使用。

交付：

- 新增统一资产查询接口：迭代读取、页读取、总数读取；弃用新代码中的无边界 `get_media_assets`。
- 搜索与列表使用 keyset/cursor 分页（排序键为 `date_imported, asset_id`）；小项目可保留 OFFSET 兼容层。
- 素材信息页由 `QTableWidget` 逐步迁移至 `QTableView + QAbstractTableModel`，实现按需载入和稳定排序。
- 归档、报告、备份校验、日志关联统计改为批处理或 SQL 聚合；仅在确实需要时构造 `MediaAsset` 对象。
- CSV 导出、报告生成和项目归档改为后台任务，显示进度、剩余工作量、取消状态和输出路径。
- 将源目录扫描抽为统一扫描器，支持扩展名集合、递归策略、取消、批量回调和错误汇总。

验收：

- 10 万记录项目的首次列表显示不全量创建 Qt 单元格。
- 搜索第一页和翻页不会阻塞主线程超过 200ms 的可感知阈值。
- 导出、报告、归档、校验期间仍能最小化窗口和响应取消。
- 取消请求在一个批次或一个文件完成后生效，并明确告知已完成和待重试数量。

### 阶段 3：统一任务平台与可维护性治理（10-14 人日）

目标：降低后续功能在并发、取消和清理上的重复风险。

交付：

- 将导入、RAW 提取、重命名、归档/恢复、报告、导出、完整性校验迁移至 `TaskViewModel` 统一接口。
- 标准化任务状态机：`queued/running/cancelling/cancelled/completed/failed/recoverable`。
- 建立任务历史表或扩展现有作业表，记录参数摘要、输出、错误、恢复动作和审计关联。
- 抽取共享组件：文件扫描器、并行目标执行器、速度计算、原子文件写入、字段注册表。
- 将 `DatabaseService` 先按接口分组，再拆为 workspace/project、asset/search、backup jobs、template/audit 等模块；保留稳定门面避免大规模调用方改动。
- 仅在关键边界使用具体异常；UI `safe_slot` 保留作最后一道展示兜底。

验收：

- 所有长任务有一致的启动、进度、取消、错误和释放行为。
- 不再由各视图直接处理 `QThread` 生命周期，特殊批处理任务也有统一封装。
- 重构后服务层测试保持通过，公共工具至少有单元测试和取消路径测试。

### 阶段 4：工作流价值功能（12-18 人日）

目标：把已有底层数据能力转化为用户可见、可交付的专业功能。

交付顺序：

1. **审计日志查看器**：按项目、事件、时间、结果、操作对象筛选；支持导出和跳转关联素材/任务。
2. **真实备份报告**：从 `backup_jobs` 和任务结果生成报告，包含目标、算法、成功/失败/跳过、校验结果、失败项和重试历史。
3. **完整性校验策略**：手动、启动后提示、应用空闲时执行三档；生成健康报告，标记丢失、哈希不匹配、未校验项。
4. **增量/差异备份**：基于目标、相对路径、大小和校验和快照，仅拷贝新增或变更文件；保留“全量验证”模式用于交付。
5. **备份重试快照优化**：任务快照持久化 `relative_path/size/mtime/checksum`，优先不扫源目录直接补拷；源文件不可用时再提示局部重扫或介质缺失。
6. **项目健康页**：集中展示未备份素材、失联路径、失败任务、待重试项、最后一次校验和磁盘容量趋势。

验收：

- 用户可从任何失败备份定位失败文件、原因、目标和可执行的恢复动作。
- 备份报告与数据库任务历史一致，可作为交付凭据。
- 增量备份对未变文件不重新复制；全量校验仍可检测目标位错误。

### 阶段 5：质量门禁与发布工程（6-10 人日）

目标：让每次发布可复现、可验证，降低跨平台交付风险。

交付：

- CI 增加 Ruff、Pyright 或 mypy、测试覆盖率阈值、依赖漏洞扫描和许可证检查。
- 运行 Python 3.11 与 3.13 测试矩阵；对 SQLite FTS5 可用和不可用两种路径执行测试。
- macOS 和 Windows 增加已打包产物的启动冒烟、数据库创建、媒体元数据降级和报告生成验证。
- 将 `rawpy`、PyAV、OpenCV 等调整为必选 extras；核心依赖和可选依赖各自明确锁定策略。
- 统一 README、CI 注释、用户文档和实际测试数量/功能承诺。

验收：

- PR 必须通过格式、类型、测试和安全门禁。
- 两个平台产物能启动并完成最小导入、备份、报告流程。
- 缺失 MediaInfo、rawpy、ffmpeg 时有明确降级提示而非功能异常。

## 7. 不应近期启动的事项

- 云同步、远程团队协作、用户权限和在线审计：需要服务端、身份、冲突解决、加密和同步协议，不能建立在当前进程内全局状态上。
- 独立个人版代码库：当前一套代码、功能开关和同一数据库格式的策略正确；复制仓库会迅速造成维护分叉。
- 仅为“去重”进行大规模模块拆分：应先建立稳定接口和测试，再按领域渐进迁移。
- 以 MD5 迁移替代数据可靠性建设：默认 XXHash64 已满足当前完整性场景，优先级应低于恢复、校验与任务闭环。

## 8. 测试与验收矩阵

| 场景 | 必须验证的行为 |
|---|---|
| 设置损坏 | 原文件被保留；应用回退默认值并告知用户；后续保存不覆盖证据 |
| 数据库迁移 | 每个历史版本可升级；重复运行幂等；失败时保留可恢复备份 |
| 任务取消 | 导入、备份、校验、导出、归档在取消后不误报成功；待处理项可恢复 |
| 拔卡/断电恢复 | 运行中作业变为可重试；只补拷可用的失败文件；显示缺失源文件 |
| 大项目 | 10 万记录的筛选、分页、导出、报告不长时间阻塞 UI，不全量创建表格对象 |
| 重定位 | 常规匹配、重名冲突、校验和匹配、用户跳过均生成审计记录 |
| 回收站 | 单个/批量恢复、保留期清理、关联标签/日志/备份位置一致 |
| 平台降级 | 无 FTS5、无 MediaInfo、无 rawpy、无 ffmpeg 时核心流程仍可完成且提示准确 |
| 打包产物 | macOS/Windows 可启动、创建数据库、执行最小导入备份报告流程 |

## 9. 风险与控制

| 风险 | 控制策略 |
|---|---|
| 大型重构引入回归 | 先加契约测试与兼容门面，每次只迁移一个调用域 |
| 软删除造成数据库膨胀 | 设置默认保留期、提供按项目清理、记录回收站占用 |
| 增量备份错误跳过已变化文件 | 以大小/mtime 初筛、校验和确认；保留全量验证选项 |
| 后台任务与 Qt 生命周期竞态 | 统一由 `TaskViewModel` 持有任务引用，测试取消和窗口关闭路径 |
| FTS 平台差异 | FTS 与 LIKE 回退建立同一查询语义测试，不把 FTS 作为唯一正确性路径 |
| 可选媒体依赖不可用 | 在能力检测层统一暴露状态，构建与运行时都验证降级体验 |

## 10. 人力与里程碑建议

按 1 名熟悉 PySide6/SQLite 的开发者估算，阶段 0 至 5 合计约 49-74 人日；若并行配置测试/发布工程支持，可缩短日历周期但不应压缩阶段 1 和阶段 2 的验收。

建议发布节奏：

- **v2.1 数据安全版**：阶段 0-1，完成配置恢复、重新链接、回收站和可诊断写操作。
- **v2.2 大项目版**：阶段 2-3，完成资产查询契约、分页/虚拟列表、统一任务平台和共享基础设施。
- **v2.3 交付与运维版**：阶段 4-5，完成审计、真实备份报告、完整性策略、增量备份和跨平台发布门禁。

## 11. 首个迭代的建议 Backlog

为尽快产生风险降低价值，首个两周迭代建议只完成以下事项：
